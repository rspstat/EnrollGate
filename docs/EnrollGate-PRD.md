# EnrollGate — 요구사항 명세서 (PRD)

> Status: Draft v0.1
> 대기 중인 결정 사항은 문서 하단 "Open Questions" 참고

---

## 1. 프로젝트 개요

**EnrollGate**는 대학 수강신청 시스템에서 발생하는 트래픽 폭주, 정원 초과 판매(재고 정합성 붕괴), 매크로/봇 남용 문제를 해결하기 위한 고성능 백엔드 시스템이다. 동시성 제어, MSA, AI 기반 이상 탐지, CI/CD 자동 배포를 하나의 도메인 안에서 통합적으로 구현하는 것을 목표로 한다.

**한 줄 정의**
> 동시에 수천 명이 몰려도 정원만큼만, 공정하게, 안정적으로 처리하는 수강신청 플랫폼

---

## 2. 문제 정의 (Background)

- 실제 대학 수강신청 시스템은 오픈 순간 짧은 시간에 트래픽이 집중되며, 이 과정에서 정원 초과 판매, 서버 다운, 매크로를 이용한 불공정 선점 등의 문제가 반복적으로 발생한다.
- 단순 CRUD로 구현하면 동시 요청 시 재고(정원) 정합성이 깨지는 Race Condition이 발생한다.
- 본 프로젝트는 이 문제를 실무에서 쓰이는 기법(분산 락, 대기열, 캐싱, 이상 탐지)으로 직접 해결해보는 것을 목적으로 한다.

---

## 3. 목표 (Goals)

### 정성적 목표
- 정원 초과 없이 정확한 신청 처리 보장
- 트래픽 폭주 상황에서도 서비스 가용성 유지
- 매크로/봇으로 인한 불공정 선점 최소화
- MSA 구조로 서비스 확장 가능성을 보여주는 아키텍처 설계

### 정량적 목표 (초안 — 확정 필요)
| 지표 | 목표치 (초안) |
|---|---|
| 동시 접속자 수 | 1,000명 동시 신청 시나리오 |
| 목표 처리량 | 초당 500~1,000 TPS (부하테스트로 확정) |
| 정원 정합성 | 오차 0건 (초과 판매 0%) |
| 대기열 진입 후 처리 지연 | 수 초~수십 초 내 순차 처리 |

> 실제 목표 수치는 k6 부하테스트 진행 후 조정 예정

---

## 4. 유저 역할 (Persona)

| 역할 | 설명 |
|---|---|
| 학생 (Student) | 로그인 후 과목 조회, 신청, 대기열 진입, 신청 취소를 수행 |
| 관리자 (Admin) | 과목/정원 등록, 실시간 신청 현황 모니터링, 이상 탐지 로그 확인 |

---

## 5. 핵심 유저 스토리

1. 학생으로서, 나는 인기 과목이 마감되기 전에 빠르고 공정하게 신청 기회를 얻고 싶다.
2. 학생으로서, 정원이 초과됐을 때 무작정 실패하기보다 대기열에서 순서를 기다리고 싶다.
3. 학생으로서, 내가 몇 번째로 대기 중인지 실시간으로 확인하고 싶다.
4. 관리자로서, 신청 폭주 상황에서 실시간 처리 현황과 이상 트래픽을 모니터링하고 싶다.
5. 관리자로서, 매크로로 의심되는 요청을 자동으로 걸러내고 싶다.

## 6. 기능 요구사항 (Functional Requirements)

### 6.1 학생 기능
- [x] 회원가입 / 로그인 (JWT 인증)
- [x] 과목 목록 조회 (실시간 잔여 정원 표시)
- [x] 과목 신청 요청
- [x] 정원 초과 시 **대기열 자동 진입**
- [x] 대기열 내 본인 순번 확인 — 1단계는 WebSocket 대신 폴링 API(`GET /queue/status`)로 대체, 실시간 push는 2단계
- [x] 순번 도달 시 신청 창구 오픈 (60초 내 확정 필요, 미확정 시 스케줄러가 다음 순번에게 기회 이전)
- [x] 신청 내역 조회 / 취소

### 6.2 관리자 기능
- [x] 과목 등록 및 정원 설정
- [ ] 실시간 신청 현황 대시보드 (신청률, 대기열 길이, TPS) — 2단계(부하테스트/메트릭 계측) 이후로 보류
- [ ] 이상 트래픽(매크로 의심) 탐지 로그 확인 — 4단계(AI 봇 탐지 연동) 과제

### 6.3 대기열 시스템 (핵심 기능)
정원 초과 시 즉시 실패시키지 않고, **가상 대기실(Virtual Waiting Room)** 방식으로 처리한다.

- 요청 도착 시각 기준으로 대기열에 순서대로 적재 (Redis Sorted Set 등 활용 예정, 세부 설계는 아키텍처 단계에서 확정)
- 대기열 순번을 **WebSocket**을 통해 실시간 양방향으로 안내 (학생 클라이언트는 접속 유지, 서버는 순번 변동 시마다 push)
- 순번이 되면 일정 시간(예: 60초) 내에 신청을 확정하도록 유도, 미확정 시 자동으로 다음 순번에게 기회 이전
- 대기열 처리 자체도 부하테스트 대상에 포함 (대기열이 병목이 되지 않도록 설계)
- WebSocket 커넥션 급증에 대비해 커넥션 관리(세션 수 제한, 재연결 처리)도 설계 범위에 포함

> 대기열 저장 구조(Redis Sorted Set 등), 토큰 기반 검증 방식은 API/아키텍처 설계 단계에서 구체화

### 6.4 AI 연동 기능
- [ ] 매크로/봇 의심 요청 탐지 (요청 간격, 반복 패턴, User-Agent 이상치 기반 이상 탐지)
- [ ] (확장) 인기 과목 수요 예측 → 사전 캐시 워밍/스케일링 트리거

## 7. 비기능 요구사항 (Non-Functional Requirements)

| 항목 | 요구사항 |
|---|---|
| 동시성 정합성 | 동시 요청 상황에서도 정원 초과 판매 0건 |
| 가용성 | 트래픽 폭주 시에도 서비스 다운 없이 대기열로 흡수 |
| 응답 우선순위 | "빠른 응답"보다 "정확한 재고 처리"를 우선 (신청 결과는 지연되더라도 정확해야 함) |
| 확장성 | 서비스별 독립 배포/스케일링 가능한 구조 (MSA) |
| 관찰 가능성 | 주요 지표(TPS, 대기열 길이, 에러율) 모니터링 가능 |
| 보안 | 인증/인가, 봇 탐지를 통한 어뷰징 방지 |

## 8. 단계별 개발 로드맵 (MVP 우선순위)

| 단계 | 범위 | 목표 |
|---|---|---|
| **1단계 (필수)** | 단일 서비스로 신청 API + 분산 락 기반 동시성 제어 + 대기열 기본 구현 | 핵심 로직 정합성 확보 |
| **2단계** | k6 부하테스트 + Redis 캐싱 적용 전/후 성능 비교 | 정량적 성능 개선 스토리 확보 |
| **3단계** | User / Enrollment / AI 서비스로 MSA 분리 | 아키텍처 확장성 증명 |
| **4단계** | 매크로 탐지 AI 모델 연동 | 이상 탐지 기능 완성 |
| **5단계** | GitHub Actions CI/CD + AWS 배포 | 실무형 배포 파이프라인 완성 |

> 시간이 부족할 경우 1~2단계까지는 반드시 완성하고, 3단계 이후는 로드맵으로 README에 명시

## 10. 성공 지표 (Success Metrics)

- 동시 요청 부하테스트에서 정원 초과 판매 0건 달성

- 대기열 시스템의 순번 처리 지연 시간 측정 및 문서화
- 매크로 탐지 정확도(정탐/오탐률) 측정
